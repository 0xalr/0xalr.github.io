🔍 introducation

During November, I dedicated most of my bug hunting efforts to access control vulnerabilities—specifically IDOR (Insecure Direct Object Reference). While IDOR is often considered a “common” issue, I quickly discovered that this vulnerability comes in many shapes and forms depending on how systems handle authorization, object visibility, and backend validation.

In this article, I will walk through the most interesting IDOR cases I found, how I identified them, and what made each one exploitable. My goal is not just to showcase reports, but to provide others (especially hunters) with real-world observations, practical angles of thinking, and patterns that may help uncover similar access control weaknesses.

Finding #1 — Unauthorized Access to Private Integrations by Overriding a Boolean Parameter.

The Functionality:

The platform allows teams to manage integrations (private integrations and marketplace ones). Normally, integrations that are private are only visible to team members with specific permissions.

In the user interface, private integrations are not displayed for general members or viewer-level users

Expected Behavior:

A user without proper access should not be able to view the team’s private integrations, and no one outside the team should be able to see them either.

What Happened:

While reviewing one of the integration-related endpoints (/api/v1/integration/{slug-integration}), the API response returned the following field:

public: false

I tried changing the integration slug to one belonging to another team, but unfortunately, I got a 401 error. I also tried several other methods, but I was unsuccessful.

But I chose the idea of ​​entering `public` as a parameter in the request and setting its value to `true`.

As I suspected, the authentication was passed and the backend server considered it to be publicly available, so the integration information was returned.

Finding #2 — Discovering Hidden API Endpoints Through Client-side JavaScript Files

During testing, I wanted to explore functions that do not appear in the user interface but might still exist logically within the application. Sometimes platforms remove features from the UI but keep the same backend endpoints active for compatibility or legacy functionality.

To identify these hidden functionalities, I inspected JavaScript source files loaded in the web application

My method for finding endpoints in JavaScript files is to search for the function within the file. For example, if the integration function has an endpoint in the following format: `/api/v2/integration`, I will take that endpoint and search for it in all JavaScript files.

It will output all the functions that fall under the endpoint, for example.

/api/v2/integration/install
/api/v2/integration/configruation

After compiling all the endpoints that fall under /api/v2/integration, start guessing according to the application. For example:

/api/v2/integration/install/{id-org||id-workspase || id-install-integration}
/api/v2/integration/installs
/api/v2/integration/configration/{id-org ||id-workspase ||id-configruation}
/api/v2/integration/configrations
/api/v2/integration/configrations/{id}
etc.......

The guessing comes from the application and the functions that are within the integration feature.

It requires patience and perseverance, but it’s worth it.

Through this method, 3 vulnerabilities were discovered.

Finding #3—Direct Data Exposure by Changing Slug/ID in API Requests

During normal usage, the application relies on identifiers (such as slugs or UUIDs) to fetch specific objects like:

Teams

Applications

Workspaces

Integrations

Projects

etc…

You can easily change the title or ID of any object, and it will return the object’s information without any authentication.
